パスワード平文保存（不適切なクレデンシャル管理）

何が起きるのか

DB に平文パスワードを入れると、SQL インジェクションや内部漏洩・バックアップ流出 1 回で ユーザーの「他サービスでも同じパスワード」まで芋づる的に漏れます（クレデンシャル・スタッフィング）。

実運用のアプリでは、一覧やプロフィールにパスワード自体を載せるような実装はほぼ想定されません。この教材では「DB に平文で保管されている」と分かりやすく伝えるために、画面上でも平文を出す構成にわざとしています。

再現手順（VULNERABLE 版）

  1. 初期データの ADMIN（admin / admin123）で /vulnerable/login からログインする。
  2. ヘッダ2 段目の「ユーザー一覧」から /vulnerable/users を開く。
  3. 一覧の各行に、ユーザー名・メールに加え パスワード列に平文（例: admin123）がそのまま載っていることを確認する。
  4. ユーザ名をクリックするとプロフィールへ遷移し、そこでも平文パスワードが表示される。
  5. 攻撃成功の目安（情報漏洩のデモ）: 画面だけでクレデンシャルが読み取れる。一覧・プロフィールのいずれでも、保存パスワードが平文のまま表示される。
  6. 対策版で比較: http://localhost:8080/secure/users は ADMIN ログイン時のみ開ける（匿名・一般ユーザはログインへ誘導されるか 403）。一覧にはパスワードは出さず、プロフィール詳細 /secure/users/{id} でも BCrypt ハッシュは画面に出さない。
  7. 組み合わせ: SQL インジェクションで DB から同じテーブルを読めた場合、平文パスワードが一括で漏洩するリスクを想像する。

VULNERABLE 側のコード

脆弱
com.example.secapp.vulnerable.dao.VulnerableUserDao #create

パスワードをハッシュ化せず、INSERT 文の文字列へ平文のまま連結している。

String sql = "INSERT INTO vuln_users (username, password, email, role) VALUES ("
        + "'" + username + "', '" + plainPassword + "', '" + email + "', 'USER')";
jdbc.update(sql);

SECURE 側のコード

対策
com.example.secapp.secure.web.SecureAuthController #doRegister

登録時に PasswordEncoder でハッシュ化してから DAO に渡す。

String hashed = passwordEncoder.encode(form.getPassword());
userDao.create(form.getUsername(), hashed, form.getEmail(), "USER");
対策
com.example.secapp.secure.dao.SecureUserDao #create

INSERT はすべてプレースホルダ。password 列にはハッシュのみが入る。

jdbc.update(
    "INSERT INTO sec_users (username, password, email, role) VALUES (?, ?, ?, ?)",
    username, hashedPassword, email, role);

対策のポイント

  • BCrypt / Argon2 / scrypt のような適応的ハッシュを使う（単純な MD5/SHA は不可）
  • ソルトはアルゴリズムが自動で付与する（BCrypt はハッシュ文字列に含まれる）
  • 画面・ログ・エラーメッセージにパスワードを出さない
  • 多要素認証 (TOTP など) を併用するとさらに強い

クロスサイトスクリプティング (XSS)

何が起きるのか

ユーザーの入力をエスケープせずに HTML として出すと、<script> タグや onerror 属性が ブラウザでそのまま実行されます。Cookie 窃取やフィッシング、ログイン状態の悪用など被害は多岐にわたります。

蓄積型 XSS の再現手順（VULNERABLE 版）

  1. http://localhost:8080/vulnerable/login を開く。
  2. ユーザー名 alice、パスワード wonderland でログイン。
  3. 上部の 新規投稿（または /vulnerable/posts/new）を開く。
  4. タイトルは任意（例: XSS test）。
  5. 本文に次をそのまま貼り付ける: 
    <script>alert('XSS by ' + document.cookie)</script>
  6. 投稿するを押す。
  7. 投稿一覧を開き直すか、さきほどの投稿の詳細を開く。
  8. 攻撃成功の目安: ブラウザのアラートが開き、メッセージに Cookie 相当の文字列が含まれる（vuln_uid は HttpOnly=false のため JS から読める設定）。
  9. 対策版で比較: /secure/... では本文がエスケープされ、同じ文字列ではスクリプトが実行されない。

反射型 XSS の再現手順（VULNERABLE）

  1. ログインの要否はありません。投稿一覧を開く。
  2. 検索欄に次を貼り付けて 検索を押す: 
    <img src=x onerror=alert(1)>
  3. 攻撃成功の目安: 一覧ページ表示時に alert(1) が実行される。
  4. URL 直アクセスでの確認: このリンクを踏むと同じ効果（アドレスバーの q= を見る）。
  5. 対策版で比較: /secure/posts で同じ検索をしてもキーワードはエスケープされ、alert(1) は動かない。

コメントでの蓄積型 XSS（おまけ）

コメント本文も vulnerable/post_detail.html で th:utext 出力されます。投稿の本文ではなく コメント欄に同じペイロードを貼って送信するだけで蓄積型 XSS が再現できます。攻撃成功の目安: 投稿詳細ページを開くたびに alert が走ります（自分のコメントなら同じ投稿詳細ページのコメント欄に出る「編集／削除」リンクから停止できることも合わせて確認できます）。

VULNERABLE 側のテンプレート

脆弱
src/main/resources/templates/vulnerable/post_detail.html post_detail.html

投稿本文を th:utext で出力しており、HTML／スクリプトがそのまま解釈される（一覧の検索ハイライトやコメント欄も同様のパターン）。

<div th:utext="${post.content}"></div>

SECURE 側のテンプレート

対策
src/main/resources/templates/secure/post_detail.html post_detail.html

th:text により自動エスケープされ、入力がそのまま HTML として評価されない。

<div th:text="${post.content}" style="white-space:pre-wrap"></div>

対策のポイント

  • 原則すべて th:text（自動 HTML エスケープ）を使う
  • th:utext はサニタイズ済み HTML を意図して扱う場面に限定する
  • セッション Cookie は HttpOnly をオンにし、可能なら Secure, SameSite=Lax も付ける
  • HTTP ヘッダで Content-Security-Policy を併用すると更に強固

おまけ: Thymeleaf 以外での出力・エスケープの例

この教材では th:text と th:utext の違いで XSS 対策を示しています。実務では JSP、SPA（React / Vue）、または JSON だけ返す API など様々ですが、共通するのはコンテキストに応じたエスケープです。HTML に埋め込むなら HTML エスケープが基本で、サニタイズ済み HTML を意図的に許可する箇所だけを別扱いにします。

JSP（JSTL）

環境によっては ${userInput} をそのまま本文に書くと解釈が変わり、エスケープされないことがあります。<c:out> は既定で XML（HTML で安全）向けにエスケープします。

<%@ taglib uri="http://java.sun.com/jsp/jstl/core" prefix="c" %>
<div><c:out value="${post.content}" /></div>

レガシーな <%=% ... %> 直呼び出しより、JSTL や Spring のフォームタグ＋適切なエスケープを優先するとよいです。

React（JSX）

テキストを子として渡すと既定でエスケープされます。dangerouslySetInnerHTML はサニタイズ済みなどごく一部でのみ。

function PostBody({ content }) {
  return <div style={{ whiteSpace: 'pre-wrap' }}>{content}</div>;
}

// ユーザー入力をそのまま渡すような使い方は原則避ける:
// <div dangerouslySetInnerHTML={{ __html: content }} />

Vue 3

マスタッシュ {{ }} はテキストとしてエスケープされます。v-html はブラウザが HTML として解釈するため、ユーザー入力には原則使いません。

<div style="white-space: pre-wrap">{{ post.content }}</div>
<!-- 危険: <div v-html="post.content"></div> （信頼できない入力に使わない） -->

Java で HTML をエスケープするだけ（テンプレート外・独自出力）

メール本文の組み立てやログ、独自ジェネレータなど、フレームワークの自動エスケープに載らないときはライブラリで明示的にエスケープします。

import org.springframework.web.util.HtmlUtils;

String safe = HtmlUtils.htmlEscape(userInput);

コンテキストが HTML の属性値・JavaScript・CSS・URL の各ケースでは、それぞれ別のエスケープ規則が必要です。OWASP XSS Prevention Cheat Sheet も参照してください。

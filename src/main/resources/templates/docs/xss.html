クロスサイトスクリプティング (XSS)

何が起きるのか

ユーザーの入力をエスケープせずに HTML として出すと、<script> タグや onerror 属性が ブラウザでそのまま実行されます。Cookie 窃取やフィッシング、ログイン状態の悪用など被害は多岐にわたります。

蓄積型 XSS の再現手順（VULNERABLE 版）

  1. http://localhost:8080/vulnerable/login を開く。
  2. ユーザー名 alice、パスワード wonderland でログイン。
  3. 上部の 新規投稿（または /vulnerable/posts/new）を開く。
  4. タイトルは任意（例: XSS test）。
  5. 本文に次をそのまま貼り付ける: 
    <script>alert('XSS by ' + document.cookie)</script>
  6. 投稿するを押す。
  7. 投稿一覧を開き直すか、さきほどの投稿の詳細を開く。
  8. 攻撃成功の目安: ブラウザのアラートが開き、メッセージに Cookie 相当の文字列が含まれる（vuln_uid は HttpOnly=false のため JS から読める設定）。
  9. 対策版で比較: /secure/... では本文がエスケープされ、同じ文字列ではスクリプトが実行されない。

反射型 XSS の再現手順（VULNERABLE）

検索キーワード q が一覧画面で th:utext 出力されるため、HTML がそのまま解釈されます。

  1. ログインの要否はありません。投稿一覧を開く。
  2. 検索欄に次を貼り付けて 検索を押す: 
    <img src=x onerror=alert(1)>
  3. 攻撃成功の目安: 一覧ページ表示時に alert(1) が実行される。
  4. URL 直アクセスでの確認: このリンクを踏むと同じ効果（アドレスバーの q= を見る）。
  5. 対策版で比較: /secure/posts で同じ検索をしてもキーワードはエスケープされ、alert(1) は動かない。

    6. VULNERABLE 側のテンプレート

    <div th:utext="${p.content}"></div>

    SECURE 側のテンプレート

    <div th:text="${p.content}" style="white-space:pre-wrap"></div>

    対策のポイント

    • 原則すべて th:text（自動 HTML エスケープ）を使う
    • th:utext はサニタイズ済み HTML を意図して扱う場面に限定する
    • セッション Cookie は HttpOnly をオンにし、可能なら Secure, SameSite=Lax も付ける
    • HTTP ヘッダで Content-Security-Policy を併用すると更に強固

認可不備 / IDOR (Insecure Direct Object Reference)

何が起きるのか

URL の {id} をその場で書き換えるだけで他人のリソースにアクセス・更新できてしまう脆弱性。 認証は通っているのに、「対象が本当に自分のものか」のチェックが抜けているのが本質。

補足（一覧と認可）: 脆弱版の「ユーザー一覧」は ADMIN にだけヘッダ2 段目（アプリ内）にリンクが出ますが、/vulnerable/users 自体にはロール検証がなく、URL を直打ちすれば未ログインでも一般ユーザでも開けます（ナビで隠すだけの認可）。下記の「未ログインでユーザー一覧」も参照。対策版では GET /secure/users を Spring Security で ADMIN のみに限定しています。一覧に平文パスワードが並ぶ問題は パスワード平文保存も参照。

再現手順（VULNERABLE 版）

未ログインでユーザー一覧が開く

  1. ログインしていない状態にする（/vulnerable/logout へアクセスして Cookie を捨てる、またはシークレットウィンドウで開くなど）。
  2. アドレスバーに http://localhost:8080/vulnerable/users を入力して Enter（または直接 /vulnerable/users）。一覧がそのまま表示される。
  3. 対策版で比較: http://localhost:8080/secure/users は匿名では開けず、ADMIN でもない一般ユーザでも拒否される。

他人のメール変更（GET）

  1. http://localhost:8080/vulnerable/login で bob / builder としてログイン（bob はユーザー ID 3）。
  2. アドレスバーを次の URL にそのまま貼り替えて Enter（ホストは環境に合わせる）: 
    http://localhost:8080/vulnerable/users/1/update-email?email=hacked@example.com
    1 は admin のユーザー ID です。
  3. 攻撃成功の目安: 実装は redirect:/vulnerable/users/{id} なので admin（ID=1）のプロフィールページに遷移する。そのページで確認するか、/vulnerable/users の一覧で admin のメールが hacked@example.com に変わっていることを確認できる。

他人の投稿の削除・編集（URL 直指定）

画面上は投稿者本人にだけ「編集・削除」ボタンを出していますが、サーバはオーナー検証をしていません。

  1. 引き続き bob でログインしたまま、新しいタブ（またはアドレスバー）で次を開く: 
    http://localhost:8080/vulnerable/posts/1/delete
    （初期データでは ID 1 は admin の「ようこそ」投稿。一覧・詳細の URL で ID を確認してよい。）
  2. 確認ダイアログなしで削除され、一覧から該当投稿が消える。
  3. 攻撃成功の目安: bob の画面では他人投稿の「削除」ボタンは出ていないが、URL 直指定だけで admin の投稿を消せている。
  4. 編集用フォーム URL 例: http://localhost:8080/vulnerable/posts/2/edit（存在する ID に変更）。POST 更新や GET 更新も認可なしで通ります（CSRF参照）。
  5. 対策版で比較: 同じ URL を試しても、Spring Security のオーナー／ADMIN チェックで拒否される。

他人のコメント削除（URL 直指定）

投稿だけでなく コメントにも同じ穴があります。画面上は本人にしか「編集／削除」リンクは出していませんが、サーバ側はオーナー検証なしです。

  1. 引き続き bob でログインしたまま、削除したい他人のコメントが付いている投稿の詳細を開き、コメント ID を控える（コメント自体の表示で ID は見えないので、自分のコメントの「編集」リンクに含まれる ?editCommentId=... や DB / ログで確認）。
  2. 新しいタブのアドレスバーに次を入力（{postId} と {commentId} は実際の値に置換）: 
    http://localhost:8080/vulnerable/posts/{postId}/comments/{commentId}/delete
  3. 攻撃成功の目安: 該当コメントが投稿詳細から消える。POST 系の /vulnerable/posts/{postId}/comments/{commentId}/update も認可なしで通り、他人のコメント本文を書き換えられる（外部オリジンの自動 submit フォームと組み合わせれば CSRF 経由でも成立）。
  4. 対策版で比較: 同じ操作は POST＋CSRF＋オーナー検証で拒否される（403）。

VULNERABLE 側のコード

脆弱
com.example.secapp.vulnerable.web.VulnerablePostController #delete

GET で削除を受け付け、投稿のオーナーかどうかをサーバ側で検証していない。

@GetMapping("/{id}/delete")
public String delete(@PathVariable Long id) {
    postDao.delete(id);  // 誰がオーナーかを確認しない
    return "redirect:/vulnerable/posts";
}

SECURE 側のコード

対策
com.example.secapp.secure.web.SecurePostController #delete

POST で受け、`ensureOwner` で投稿者本人または ADMIN に限定したうえで削除する。

@PostMapping("/{id}/delete")
public String delete(@PathVariable Long id, @AuthenticationPrincipal SecurePrincipal me) {
    Post post = postDao.findById(id).orElse(null);
    if (post == null) return "redirect:/secure/posts";
    ensureOwner(post, me); // 投稿者本人 or ADMIN だけ通す
    postDao.delete(id);
    return "redirect:/secure/posts";
}

対策のポイント

  • 「認証されているか」と「そのリソースの所有者か」を必ず別々に確認する
  • サーバー側でオーナー判定を行う（クライアント側の隠し input 等は信用しない）
  • URL に他人の ID を入れて成立してしまう操作はないか、CRUD ごとに棚卸しする
  • 必要に応じて @PreAuthorize や @PostAuthorize を使う

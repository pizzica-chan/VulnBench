認可不備 / IDOR (Insecure Direct Object Reference)

何が起きるのか

URL の {id} をその場で書き換えるだけで他人のリソースにアクセス・更新できてしまう脆弱性。 認証は通っているのに、「対象が本当に自分のものか」のチェックが抜けているのが本質。

再現手順（VULNERABLE 版）

他人のメール変更（GET）

  1. http://localhost:8080/vulnerable/login で bob / builder としてログイン（bob はユーザー ID 3）。
  2. アドレスバーを次の URL にそのまま貼り替えて Enter（ホストは環境に合わせる）: 
    http://localhost:8080/vulnerable/users/1/update-email?email=hacked@evil.com
    1 は admin のユーザー ID です。
  3. 攻撃成功の目安: プロフィールなどにリダイレクトされ、ユーザー一覧で admin のメールが hacked@evil.com になっている。

他人の投稿の削除・編集（URL 直指定）

画面上は投稿者本人にだけ「編集・削除」ボタンを出していますが、サーバはオーナー検証をしていません。

  1. 引き続き bob でログインしたまま、新しいタブ（またはアドレスバー）で次を開く: 
    http://localhost:8080/vulnerable/posts/1/delete
    （初期データでは ID 1 は admin の「ようこそ」投稿。一覧・詳細の URL で ID を確認してよい。）
  2. 確認ダイアログなしで削除され、一覧から該当投稿が消える。
  3. 攻撃成功の目安: bob の画面では他人投稿の「削除」ボタンは出ていないが、URL 直指定だけで admin の投稿を消せている。
  4. 編集用フォーム URL 例: http://localhost:8080/vulnerable/posts/2/edit（存在する ID に変更）。POST 更新や GET 更新も認可なしで通ります（CSRF参照）。
  5. 対策版で比較: 同じ URL を試しても、Spring Security のオーナー／ADMIN チェックで拒否される。

VULNERABLE 側のコード

// VulnerablePostController#delete
@GetMapping("/{id}/delete")
public String delete(@PathVariable Long id) {
    postDao.delete(id);  // 誰がオーナーかを確認しない
    return "redirect:/vulnerable/posts";
}

SECURE 側のコード

// SecurePostController#delete
@PostMapping("/{id}/delete")
public String delete(@PathVariable Long id, @AuthenticationPrincipal SecurePrincipal me) {
    Post post = postDao.findById(id).orElseThrow();
    ensureOwner(post, me); // 投稿者本人 or ADMIN だけ通す
    postDao.delete(id);
    return "redirect:/secure/posts";
}

対策のポイント

  • 「認証されているか」と「そのリソースの所有者か」を必ず別々に確認する
  • サーバー側でオーナー判定を行う（クライアント側の隠し input 等は信用しない）
  • URL に他人の ID を入れて成立してしまう操作はないか、CRUD ごとに棚卸しする
  • 必要に応じて @PreAuthorize や @PostAuthorize を使う

セッション管理不備

何が起きるのか

VULNERABLE 版は「ログイン後に vuln_uid=<userId> という Cookie を発行する」だけの自前認証です。 Cookie に署名がなく値も推測可能なので、ブラウザの開発者ツールで vuln_uid=1 に書き換えるだけで admin になりすませます。

再現手順（VULNERABLE 版）

  1. http://localhost:8080/vulnerable/login を開く。
  2. ユーザー名 bob、パスワード builder でログインする。
  3. 投稿一覧を開き、見出し「投稿一覧」の右に「bob でログイン中」と表示されていることを確認（このとき Cookie vuln_uid は通常 3 = bob の ID）。
  4. 開発者ツールで Cookie を編集: F12 → ストレージ／アプリケーション（ブラウザにより名称差あり）→ Cookies → http://localhost:8080 → vuln_uid の値を 1 に変更して保存。
  5. 同じタブで 投稿一覧を再読み込み（F5）。
  6. 攻撃成功の目安: 投稿一覧の見出し横の表示が admin に変わる（サーバは Cookie の数字だけをユーザ ID として信じている）。ヘッダ 2 段目のマイプロフィールリンクも admin のページを指すようになる。
  7. 補足: XSS と組み合わせる想定では、HttpOnly が付いていないため JavaScript の document.cookie でも vuln_uid を読める設定になっています。
  8. 対策版で比較: vuln_uid は使わず、サーバ発行のセッション Cookie（HttpOnly 等）を使うため、同様の改ざんは成立しません。

VULNERABLE 側のコード

脆弱
com.example.secapp.vulnerable.auth.LegacyCookieAuth #login

ユーザ ID をそのまま Cookie に載せ、かつ HttpOnly=false でスクリプトから読めるようにしている（推測可能なセッション相当情報）。

Cookie cookie = new Cookie("vuln_uid", String.valueOf(userId));
cookie.setHttpOnly(false); // 故意の設定
res.addCookie(cookie);

SECURE 側のコード

対策
com.example.secapp.config.SecurityConfig #secureFilterChain

サーバ発行のセッションを前提とし、ログイン後にセッション ID を再生成して固定化を抑止する。

...
.sessionManagement(s -> s
    .sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED)
    .sessionFixation(sf -> sf.changeSessionId()))
...
対策
src/main/resources/application.yml servlet.session.cookie

対策サイト用セッション Cookie 名と http-only 等のアプリ共通設定。

servlet:
  session:
    cookie:
      name: SECAPP_SESSION
      http-only: true

対策のポイント

  • セッション ID はサーバー側で生成し、Cookie には推測不可能な値だけを格納する
  • ログイン直後にセッション ID を再生成（changeSessionId）してセッション固定化を防ぐ
  • Cookie には HttpOnly, Secure, SameSite=Lax を付ける
  • ログアウト時はサーバー側のセッションも無効化する（invalidateHttpSession(true)）

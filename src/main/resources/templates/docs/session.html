セッション管理不備

何が起きるのか

VULNERABLE 版は「ログイン後に vuln_uid=<userId> という Cookie を発行する」だけの自前認証です。 Cookie に署名がなく値も推測可能なので、ブラウザの開発者ツールで vuln_uid=1 に書き換えるだけで admin になりすませます。

再現手順（VULNERABLE 版）

  1. VULNERABLE 版で bob としてログイン（Cookie は vuln_uid=3）
  2. ブラウザの DevTools → Application → Cookies で vuln_uid を 1 に書き換える
  3. そのまま /vulnerable/posts をリロードすると admin として表示される
  4. XSS 経由でも、Cookie に HttpOnly がないので document.cookie で読める

VULNERABLE 側のコード

Cookie cookie = new Cookie("vuln_uid", String.valueOf(userId));
cookie.setHttpOnly(false); // 故意の設定
res.addCookie(cookie);

SECURE 側のコード

// SecurityConfig
.sessionManagement(s -> s
    .sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED)
    .sessionFixation(sf -> sf.changeSessionId()))
// application.yml
servlet:
  session:
    cookie:
      name: SECAPP_SESSION
      http-only: true

対策のポイント

  • セッション ID はサーバー側で生成し、Cookie には推測不可能な値だけを格納する
  • ログイン直後にセッション ID を再生成（changeSessionId）してセッション固定化を防ぐ
  • Cookie には HttpOnly, Secure, SameSite=Lax を付ける
  • ログアウト時はサーバー側のセッションも無効化する（invalidateHttpSession(true)）

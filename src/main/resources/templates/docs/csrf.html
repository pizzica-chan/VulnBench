クロスサイトリクエストフォージェリ (CSRF)

何が起きるのか

被害者がログイン中のサイトに対して、攻撃者の用意したページから「意図しないリクエスト」を発射させる攻撃。 ログイン中の Cookie はブラウザが自動送信するため、被害者が気づかない間に投稿削除や設定変更が走ります。

再現手順（VULNERABLE 版）

「ログイン済みのブラウザが、クリック一つ／タブ一つでGET による状態変更を意図せず実行してしまう」イメージで確認します。

  1. http://localhost:8080/vulnerable/login でログイン（例: alice / wonderland）。
  2. 投稿一覧を開き、削除してよい投稿 IDを確認する（初期データでは「ようこそ」が id=1、alice の「初投稿」が id=2 など。詳細ページの URL の数字が ID）。
  3. 方法 A（確実・手順が短い）: ログインしたまま 新しいタブを開き、アドレスバーに 
    http://localhost:8080/vulnerable/posts/1/delete
    のように /vulnerable/posts/{id}/delete を入力して Enter（{id} は手順2で決めた値）。確認ダイアログは出ません（一覧画面の「削除」ボタンには JavaScript の confirm が付いていますが、この手順はアドレスバー直打ちのため onclick ハンドラが走らない＝そのまま削除リクエストが飛びます）。即リダイレクトされ投稿が消えます。
    同じ要領で /vulnerable/posts/{postId}/comments/{commentId}/delete もコメント単位で GET 削除が成立します（IDOR参照）。
  4. 方法 B（CSRF の典型イメージ・自動 submit フォーム）: 次のような HTML を ローカルの別ファイル（例: attacker.html）として保存し、ログイン済みの同じブラウザで開く。ページを開いた瞬間にスクリプトがフォームを送信し、top-level navigation として /vulnerable/posts/1/delete へ遷移する。 
    <!doctype html>
<html><body>
<p>ただのキャンペーンページ……</p>
<form id="x" action="http://localhost:8080/vulnerable/posts/1/delete" method="get"></form>
<script>document.getElementById('x').submit();</script>
</body></html>

    最近のブラウザは Cookie が既定で SameSite=Lax のため、外部オリジンの <img> など「サブリソース GET」には Cookie が付かないことがあります。一方で <form> の submit や <a> クリックといった top-level navigation の GET には Cookie が付与されるため、上記のフォーム自動 submit パターンが教材では再現性が高いです。それでも遷移時の確認ダイアログ等で止まる場合は 方法 A で「GET 削除」の危険性は同等に確認できます。

  5. GET による更新: ログイン不要な実装のため、同様にアドレスバーへ 
    http://localhost:8080/vulnerable/posts/1/update?title=hacked&content=hacked
    のように貼ると、認可チェックなく更新されます（id は存在する投稿に合わせる）。
  6. 攻撃成功の目安: 削除なら一覧から該当投稿が消えている。GET 更新なら該当投稿を開き、タイトル・本文が hacked に変わっている。
  7. 対策版で比較: 削除・更新は POST＋CSRF トークンが必要なため、同じ URL を踏んでも成立しません。

VULNERABLE 側のコード

各コードブロック直上の参照バーに、その抜粋のクラス・メソッド（またはファイルパス）を示しています。

脆弱
com.example.secapp.vulnerable.web.VulnerablePostController 状態変更エンドポイント

削除・更新をGETで受け付けているため、意図せない遷移・画像読み込み・フォーム submit だけで状態が変わり得る。

@GetMapping("/{id}/delete")
public String delete(@PathVariable Long id) { ... }

@GetMapping("/{id}/update")
public String updateViaGet(@PathVariable Long id,
                           @RequestParam String title,
                           @RequestParam String content) { ... }
脆弱
com.example.secapp.config.SecurityConfig #permissiveFilterChain

脆弱版ルート側のフィルタチェーンで CSRF 保護をオフにしており（POST があっても）トークン検証が行われない。

http
        .securityMatcher("/**")
        .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
        .csrf(csrf -> csrf.disable())
        .formLogin(form -> form.disable())
        ...
        return http.build();

SECURE 側のコード

対策版も緑の参照バーで、抜粋の所在を同じ見せ方で示しています。

対策
com.example.secapp.config.SecurityConfig #secureFilterChain

/secure/** 向けチェーンでは Spring Security のデフォルトで CSRF 検証が有効。

http
        .securityMatcher("/secure/**")
        ...
        .csrf(Customizer.withDefaults())
対策
com.example.secapp.secure.web.SecurePostController #update / #delete

更新・削除は @PostMapping のみとし、フォームから CSRF トークンと共に送る。

@PostMapping("/{id}/update")
public String update(...) { ... }

@PostMapping("/{id}/delete")
public String delete(...) { ... }

対策のポイント

  • 状態を変えるリクエストは GET ではなく POST/PUT/DELETE にする
  • CSRF トークン（Spring Security が自動で隠しフィールドに埋め込む）を必ず検証する
  • SameSite=Lax Cookie も併用すると効果的

クロスサイトリクエストフォージェリ (CSRF)

何が起きるのか

被害者がログイン中のサイトに対して、攻撃者の用意したページから「意図しないリクエスト」を発射させる攻撃。 ログイン中の Cookie はブラウザが自動送信するため、被害者が気づかない間に投稿削除や設定変更が走ります。

再現手順（VULNERABLE 版）

  1. http://localhost:8080/vulnerable/login でログイン（例: alice / wonderland）。
  2. 投稿一覧を開き、必要なら投稿 IDを確認する（初期データでは「ようこそ」id=1、alice「初投稿」id=2、bob「雑談」id=3 など。詳細ページの URL の数字が ID）。
  3. 方法 A（確実・手順が短い）: ログインしたまま 新しいタブを開き、アドレスバーに 
    http://localhost:8080/vulnerable/posts/1/delete
    のように /vulnerable/posts/{id}/delete を入力して Enter（例では id=1。{id} は存在する投稿に合わせる）。
  4. 方法 B（CSRF の典型イメージ・自動 submit フォーム）: 次のような HTML を ローカルの別ファイル（例: attacker.html）として保存し、ログイン済みの同じブラウザで開く。 
    <!doctype html>
<html><body>
<p>ただのキャンペーンページ……</p>
<form id="x" action="http://localhost:8080/vulnerable/posts/2/delete" method="get"></form>
<script>document.getElementById('x').submit();</script>
</body></html>

    最近のブラウザは Cookie が既定で SameSite=Lax のため、外部オリジンの <img> など「サブリソース GET」には Cookie が付かないことがあります。一方で <form> の submit や <a> クリックといった top-level navigation の GET には Cookie が付与されるため、上記のフォーム自動 submit パターンが教材では再現性が高いです。それでも遷移時の確認ダイアログ等で止まる場合は 方法 A で「GET 削除」の危険性は同等に確認できます。

  5. GET による更新: ログイン不要な実装のため、同様にアドレスバーへ 
    http://localhost:8080/vulnerable/posts/3/update?title=hacked&content=hacked
    のように貼ると、認可チェックなく更新されます（例では id=3）。
  6. 攻撃成功の目安: 削除なら一覧から該当投稿が消えている。GET 更新なら該当投稿を開き、タイトル・本文が hacked に変わっている。
  7. 対策版で比較: 削除・更新は POST＋CSRF トークンが必要なため、同じ URL を踏んでも成立しません。

VULNERABLE 側のコード

脆弱
com.example.secapp.vulnerable.web.VulnerablePostController 状態変更エンドポイント

削除・更新をGETで受け付けているため、意図せない遷移・画像読み込み・フォーム submit だけで状態が変わり得る。

@GetMapping("/{id}/delete")
public String delete(@PathVariable Long id) { ... }

@GetMapping("/{id}/update")
public String updateViaGet(@PathVariable Long id,
                           @RequestParam String title,
                           @RequestParam String content) { ... }
脆弱
com.example.secapp.config.SecurityConfig #permissiveFilterChain

脆弱版ルート側のフィルタチェーンで CSRF 保護をオフにしており（POST があっても）トークン検証が行われない。

http
        .securityMatcher("/**")
        .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
        .csrf(csrf -> csrf.disable())
        .formLogin(form -> form.disable())
        ...
        return http.build();

SECURE 側のコード

対策
com.example.secapp.config.SecurityConfig #secureFilterChain

/secure/** 向けチェーンでは Spring Security のデフォルトで CSRF 検証が有効。

http
        .securityMatcher("/secure/**")
        ...
        .csrf(Customizer.withDefaults())
対策
com.example.secapp.secure.web.SecurePostController #update / #delete

更新・削除は @PostMapping のみとし、フォームから CSRF トークンと共に送る。

@PostMapping("/{id}/update")
public String update(...) { ... }

@PostMapping("/{id}/delete")
public String delete(...) { ... }

対策のポイント

  • 状態を変えるリクエストは GET ではなく POST/PUT/DELETE にする
  • CSRF トークン（Spring Security が自動で隠しフィールドに埋め込む）を必ず検証する
  • SameSite=Lax Cookie も併用すると効果的

おまけ: Spring Security 以外での CSRF 対策の例

この教材は Spring Security の CSRF フィルタが POST ごと検証する流れです。他スタックでも状態を変える処理は POST など安全なメソッドに限定し、攻撃ページから捏造しにくい秘密（トークンやカスタムヘッダなど）をサーバーで照合する、という構図は共通です。

Django

設定で django.middleware.csrf.CsrfViewMiddleware が有効なのが普通です。POST するフォームにトークンを埋め込みます。

<form method="post">
  {% csrf_token %}
  ...
</form>

Laravel（Blade）

App\Http\Middleware\VerifyCsrfToken が Web ルートに適用されます。フォームには @csrf を置くか、SPA ではメタからトークンを読んで X-XSRF-TOKEN ヘッダに載せます。

<form method="post" action="/posts">
  @csrf
  ...
</form>

Ruby on Rails

protect_from_forgery が既定で有効です。form_with／form_for には authenticity_token が自動で付きます。

<%= form_with model: @post do |f| %>
  ...
<% end %>

Express（Node.js）での「トークンを自分で検証する」イメージ

csurf は広く参照されていた一方で開発終了しており、新規には代替ライブラリやフレームワーク組み込みを選ぶことが多いです。手書きでやる場合の流れは次のイメージです。

  1. サーバーは利用者ごとのセッションに、推測されにくい秘密（シークレット）を一度だけ格納する。
  2. フォームを表示するとき、その秘密から計算したトークン文字列を hidden フィールドなどに載せ、利用者のブラウザに渡す。
  3. POST を受け取ったら、リクエストに付いているトークンが「このセッションの秘密と対になっているか」を検証し、合っていなければ拒否する。

攻撃者のページからは「勝手に POST を飛ばす」ことはできますが、被害者のブラウザの中にだけある正しいトークンを読み取れない（別サイトなので）ため、トークンなし・偽物の POST にはなりやすく、これで防げます。csrf（npm）などは、この秘密の生成とトークンの作成・検証をライブラリに任せるためのものです。

const Tokens = require('csrf');
const csrf = new Tokens();

// ログイン後などセッションに secret を保存
req.session.csrfSecret = csrf.secretSync();

// フォーム表示時: csrf.create(req.session.csrfSecret) を hidden に埋め込む
// POST 時: csrf.verify(req.session.csrfSecret, req.body._csrf)

JSON API と Cookie セッションだけの SPA

ブラウザの「単純なフォーム POST」だけでなく、fetch で JSON を送り Cookie だけでログイン状態を伝える場合でも CSRF が成立し得ます。代表的な組み立ては（1）ログイン応答やメタから CSRF トークンを渡しカスタムヘッダやヘッダ名付きフィールドで毎回送る、（2）Bearer など Second factor で Cookie に依存しない、に分かれます。詳細は OWASP CSRF Prevention Cheat Sheet が整理されています。

SQL インジェクション (SQLi)

何が起きるのか

ユーザー入力を SQL 文字列に直接連結すると、入力に ' OR '1'='1 などを混ぜられたとき 本来意図した条件式が破壊され、認証バイパスやデータ漏洩・破壊が起きます。

攻撃ペイロード例

  1. VULNERABLE 版のログイン画面 (/vulnerable/login) を開く
  2. ユーザー名に ' OR '1'='1' -- を入力（最後にスペース）
  3. パスワードは何でも良い（例: x）
  4. 送信すると、最初に見つかったユーザー（admin）として認証されてしまう

検索画面 (/vulnerable/posts?q=...) でも、 q を SQL に埋め込んでいるので UNION SELECT で別テーブルを引くこともできます。

VULNERABLE 側のコード

// VulnerableUserDao#findForLogin
String sql = "SELECT * FROM vuln_users "
        + "WHERE username = '" + username + "' "
        + "AND password = '" + password + "'";
jdbc.queryForObject(sql, ROW_MAPPER);

SECURE 側のコード

// SecureUserDao#findByUsername + SecureUserDetailsService
jdbc.queryForObject(
    "SELECT * FROM sec_users WHERE username = ?",
    ROW_MAPPER, username);
// パスワードは BCryptPasswordEncoder#matches で照合（生 SQL に乗せない）

対策のポイント

  • 必ずパラメータ化クエリ（? または :name）を使う
  • パスワードはハッシュ化してから保存し、SQL 上で = 比較しない
  • 入力サニタイズに頼らず、SQL の構文と値を分離する

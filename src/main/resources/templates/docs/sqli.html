SQL インジェクション (SQLi)

何が起きるのか

ユーザー入力を SQL 文字列に直接連結すると、入力に ' OR '1'='1 などを混ぜられたとき 本来意図した条件式が破壊され、認証バイパスやデータ漏洩・破壊が起きます。

再現手順（ログイン SQLi・VULNERABLE）

  1. アドレスバーに http://localhost:8080/vulnerable/login を入力するか、画面上部の 脆弱版 → ログインへ進む。
  2. ユーザー名欄に次をそのまま貼り付ける（末尾のハイフン2つ＋スペースまで含める）: 
    ' OR 1=1 --
  3. パスワードは任意（例: x）。
  4. ログインボタンを押す。
  5. 攻撃成功の目安: 「投稿一覧」などに飛び、画面上部に admin と表示される（複数行ヒット時は先頭ユーザとしてログイン扱い）。
  6. 別パターン: 同じ趣旨で ' OR '1'='1' -- （比較式版）も成立します。' の数や -- 後のスペースに注意。
  7. 対策版で比較: /secure/login で同じ文字列を試すとログインできない。

再現手順（投稿検索・VULNERABLE）

  1. 投稿一覧（/vulnerable/posts）を開く。
  2. 比較用に、検索欄に 雑談 だけ入れて検索し、ヒットが 1 件程度に絞られることを確認する。
  3. 検索欄を空にしてから、次をそのまま貼り付けて検索する（末尾に半角スペースあり。シングルクォートに注意）: 
    x' OR 1=1 --
  4. 攻撃成功の目安: 手順 2 より明らかに多くの投稿が一覧に出る（OR 1=1 で条件が常に真になり、行末コメント -- で後半の OR p.content LIKE … などが無効化されるため）。
  5. 同じ文字列を 対策版の投稿一覧の検索に入れても、キーワードはパラメータとしてバインドされるだけなので、「x' OR 1=1 -- 」を含む文字列の普通の部分一致検索になり、上記のような「全件に近い表示」にはならない。
  6. （任意）アドレスバーで試す場合: このリンク（GET で同じ q）

VULNERABLE 側のコード

脆弱
com.example.secapp.vulnerable.dao.VulnerableUserDao #findForLogin

入力されたユーザー名・パスワードを SQL の文字リテラルへそのまま連結している。

String sql = "SELECT * FROM vuln_users "
        + "WHERE username = '" + username + "' "
        + "AND password = '" + password + "'";
List<User> list = jdbc.query(sql, ROW_MAPPER);
脆弱
com.example.secapp.vulnerable.dao.VulnerablePostDao #search

検索キーワードを LIKE のパターン文字列へ連結している。

String sql = SELECT_BASE
        + "WHERE p.title LIKE '%" + keyword + "%' "
        + "OR p.content LIKE '%" + keyword + "%' "
        + "ORDER BY p.id DESC";

SECURE 側のコード

対策
com.example.secapp.secure.dao.SecureUserDao #findByUsername

SQL にはユーザー名だけ渡してユーザ行を検索する（? でバインド）。ログイン時に画面上で打ったその場のパスワードは SQL 文へは入れず、WHERE password = … のような比較もしない。DB から取れるのはあらかじめ保存してあるパスワードのハッシュ文字列だけで、それと入力パスワードを突き合わせるのはSQL の外（Spring Security の認証処理と BCryptPasswordEncoder の matches）になっている。

public Optional<User> findByUsername(String username) {
    try {
        return Optional.ofNullable(jdbc.queryForObject(
            SELECT_COLUMNS + "WHERE username = ?",
            ROW_MAPPER, username));
    } catch (EmptyResultDataAccessException e) {
        return Optional.empty();
    }
}
対策
com.example.secapp.secure.dao.SecurePostDao #search

LIKE も値はすべてプレースホルダ。ワイルドカード文字もエスケープし、検索語を SQL の構造と混ぜない。

String like = "%" + escapeLike(keyword) + "%";
jdbc.query(
    SELECT_BASE
        + "WHERE p.title LIKE ? ESCAPE '\\\\' "
        + "OR p.content LIKE ? ESCAPE '\\\\' "
        + "ORDER BY p.id DESC",
    ROW_MAPPER, like, like);

対策のポイント

  • 必ずパラメータ化クエリ（? または :name）を使う
  • パスワードはハッシュ化してから保存し、SQL 上で = 比較しない
  • 入力サニタイズに頼らず、SQL の構文と値を分離する

おまけ: 代表的な DB アクセスでのパラメータバインド例

この教材の対策版は Spring JdbcTemplate です。実務では MyBatis や JPA もよく使われるため、値をプレースホルダにバインドする形の例を抜粋します（SQL 文字列にユーザー入力を連結しない）。

MyBatis

マッパー XML や @Select では #{} が JDBC のプリペアド・ステートメント用の値バインドになります。${} は SQL にそのまま文字列として差し込まれるだけなので、ユーザーが操作できる入力を渡すと SQL インジェクションの原因になります。

どうしても ${} が要る場合（並び順のキーや別テーブルを切り替えるなど）は、許可リストに無い名前は拒否するなど、サーバー側で強く絞った識別子だけを渡してください。

<!-- Mapper XML の例 -->
<select id="findByUsername" resultType="com.example.User">
  SELECT id, username, password FROM users WHERE username = #{username}
</select>

<!-- 検索 LIKE の例（パターンは Java 側で組み立てて引数に渡す） -->
<select id="search" resultType="com.example.Post">
  SELECT * FROM posts
  WHERE title LIKE #{pattern} OR content LIKE #{pattern}
</select>
// アノテーション API の例
@Select("SELECT * FROM users WHERE username = #{username}")
User findByUsername(String username);

Spring JdbcTemplate

jdbcTemplate.queryForObject(
    "SELECT * FROM users WHERE username = ?",
    rowMapper,
    username);

JPA / Spring Data JPA（JPQL）

@Query("SELECT u FROM User u WHERE u.username = :username")
Optional<User> findByUsername(@Param("username") String username);

// ネイティブ SQL でも位置・名前パラメータでバインドする
@Query(value = "SELECT * FROM users WHERE username = ?1", nativeQuery = true)
Optional<User> findByUsernameNative(String username);

メソッド名からクエリを生成するだけの派生クエリ（findByUsername(String username) など）も、実装はパラメータバインドになります。

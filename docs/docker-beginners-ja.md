## 1. これだけ押さえる用語

### イメージとコンテナ

- **イメージ**は「コンテナを起動するときの設計図＋ファイル一式」のスナップショットです。読み取り中心で、同じイメージから何台でもコンテナを作れます。
- **コンテナ**は、そのイメージを実体化した**実行中（または停止中）のプロセス群とファイルシステム**です。消えれば中身も消える部分があります（後述の「永続化」）。

### Dockerfile の役割

- **Dockerfile**はイメージの**作り方**を手順書として書いたファイルです。`FROM` で土台を選び、`COPY` や `RUN` でファイルを入れたりコマンドを実行し、最終的にどのプロセスを動かすか（`ENTRYPOINT` / `CMD`）を決めます。

### Docker Compose とは

- **Compose**は、`docker-compose.yml`（または `compose.yml`）に**複数サービス**（Web、DB など）を宣言し、`docker compose up` でまとめて起動する仕組みです。単体の `docker build` / `docker run` を何度も繰り返す代わりに、再現可能な環境として扱えます。

### ポート公開

- 書式 `"ホスト側ポート:コンテナ側端口"` で、PC からコンテナ内のサーバーにアクセスする口を開きます。
- 例: `"8080:8080"` は、自分のマシンの `8080` にアクセスすると、コンテナの `8080` に転送されます。

### コンテナ同士の名前解決

- Compose が作る**デフォルトのネットワーク**内では、**サービス名**（`docker-compose.yml` のトップレベルキー、例: `mysql`）が、他のコンテナから見たときの**ホスト名**として使われます。
- だからアプリの接続設定でデータベースのホストに `localhost` ではなく `mysql` と書く、というパターンがよく出ます（後述の例）。

## 2. 例：Dockerfile を読む（マルチステージビルド）

このリポジトリの [Dockerfile](../Dockerfile) は、**ビルド用の大きなイメージ**と**実行用の小さなイメージ**を分ける**マルチステージ**構成です。

- 最初の `FROM ... AS build` ～ `RUN mvn ... package` までで **JAR ファイルをビルド**する。
- 続く `FROM eclipse-temurin:21-jre-alpine` は **Java 実行環境だけ**の土台。`COPY --from=build` で、前ステージでできた `secapp.jar` だけを持ってくる。
- 結果として、最終イメージに Maven やソースツリー全体を載せずに済み、イメージが小さく保たれやすい。

`EXPOSE 8080` は「このコンテナは 8080 で待ち受ける想定」という**文書化・連携用**の宣言で、ポートを自動で開く魔力があるわけではありません（実際の公開は `docker-compose.yml` の `ports` などで行います）。

`ENTRYPOINT ["java", "-jar", "app.jar"]` はコンテナ起動時に**必ず実行されるコマンド**です。

## 3. 例：docker-compose.yml を読む

このリポジトリの [docker-compose.yml](../docker-compose.yml) から、Compose の読み方の型を掴みます。

- **`services`**: ここに並ぶ `mysql` と `app` が、それぞれ**別コンテナ**として起動します。
- **`image`**: 公開イメージ（例: `mysql:8.0`）をそのまま使う。
- **`build: .` + `image: secapp-web`**: カレントディレクトリの Dockerfile からビルドし、できたイメージに名前 `secapp-web` を付ける。
- **`environment`**: コンテナ内の環境変数。ここで DB の初期パスワードや、アプリの Spring プロファイルなどを渡しています。
- **`ports`**: 前述のホストとコンテナのポート対応。
- **`depends_on` + `condition: service_healthy`**: `app` は `mysql` の**ヘルスチェックが成功してから**起動する、という順序制御。DB が受け付け可能になる前にアプリだけ先に立ち上がる事故を減らします。
- **`healthcheck`（mysql 側）**: `mysqladmin ping` で「DB が応答するまで」を検知し、**healthy** と判定されるまで待てます。

### （このリポジトリ固有）tmpfs と永続化の対比

```yaml
    # 永続ボリュームにしない。コンテナ再作成／再起動のたびに空の DB から起動（教材用に毎回同じ初期データ）。
    tmpfs:
      - /var/lib/mysql
```

MySQL のデータディレクトリを **tmpfs（メモリ上の一時領域）**に載せているため、コンテナを作り直すと DB 内容はリセットされやすい、という**教材向けの選択**です。

**一般論:** 本番や通常の開発では、名前付きボリュームなどで `/var/lib/mysql` を**永続化**し、コンテナを再作成してもデータが残るようにすることが多いです。ここは「Docker でデータをどう残すか」の学習ポイントとして覚えておけば十分で、**アプリ固有の仕様説明**ではありません。

## 4. 例：プロファイルと JDBC のホスト名 `mysql`

Compose の `app` サービスには次があります。

```yaml
    environment:
      SPRING_PROFILES_ACTIVE: docker
```

このリポジトリでは、プロファイル `docker` が有効なときだけ [application-docker.yml](../src/main/resources/application-docker.yml) が読み込まれ、データソース URL が **ホスト `mysql`** を指します（Compose のサービス名と一致）。

```
jdbc:mysql://mysql:3306/secapp?...
```

自分の PC 上でブラウザや `curl` から `mysql` というホスト名に繋ぐ話ではなく、**Compose の同一ネットワーク内でコンテナ同士がサービス名で通信する**典型例です。ローカルで Maven だけ動かし DB だけ Docker、というときは [README.md](../README.md) のとおり `localhost:3306` 側の設定になり、環境が切り替わる、という理解でつながります。

## 5. よく使うコマンド（一般の目的 + この例でのサービス名）

| 目的 | コマンド例 | このリポジトリでの補足 |
|------|------------|-------------------------|
| ビルドしてバックグラウンド起動 | `docker compose up --build -d` | `mysql` と `app` の両方が起動します。初回ビルドは時間がかかることがあります。 |
| 状態確認 | `docker compose ps` | サービス名 `mysql` / `app` と状態が表示されます。 |
| ログを見る | `docker compose logs -f` または `docker compose logs -f app` | `-f` は追従（tail）。止めるときは Ctrl+C。 |
| 止める | `docker compose down` | ネットワークなども整理されます（データは tmpfs の仕様に依存）。 |
| コンテナのみ再起動（イメージはそのまま） | `docker compose restart` | ソース変更はコンテナに入りません。 |
| アプリだけ再ビルドして載せ替え | `docker compose up -d --build --force-recreate app` | このリポジトリでは Windows から WSL 向けに [README.md](../README.md) の `one-click-wsl-restart` / `wsl-restart.sh` がこの操作です。MySQL は通常そのままです。 |

リポジトリ直下で実行する前提は [README.md](../README.md) の「手動（docker compose のみ）」と同じです。
